burl: the merkle merge, as a working model

How a task note breaks into hashes, how the history of root hashes is kept, and what happens block by block when a copy of a notebook is merged back into the notebook it came from. Everything below the words section is computed on this page, not drawn: every hash is a real SHA-256 over the exact bytes burl hashes, so a value here can be checked against a real .burl file with sqlite3 (how, at the end). Edit the Mine and Theirs text and everything recomputes.

Line numbers cite burl at commit 5ddb31ef. Where the page could not verify a rule it says so in place rather than guessing. The one behaviour on this page that had no test under it before it was drawn now has one: backend/spec/import_remint_spec.cr.

Words this page uses

burl is a note-taking program whose notebook is one SQLite file, something.burl. One sentence each for the terms that follow, in the order they are needed.

note
One entry in the notebook: a title, a format (this page's note is a todotxt task list), some settings, and a body of text.
block
One line of a note's body; the body is exactly the blocks' texts joined with newlines, and a blank line is a block whose text is empty.
stable id
A random 32-hex-character identity every note and every block carries, so two files can talk about "the same block" without comparing text or position.
object
A fixed byte string describing one block, one note, or the whole tree, stored under the SHA-256 of itself in an append-only table; the hash is the object's name.
tag
The first field of every object, naming its kind and version (burl-block-v1, burl-note-v3, burl-tree-v2), so a reader can never mistake one kind for another.
root
The one object at the top: it lists the hashes of the top-level notes, so its hash summarises the entire notebook and changes whenever anything under it changes.
named roots (merkle_roots)
A table of names pointing at root hashes; a root that nothing names is garbage and gets collected, so these names are what keeps history alive.
live
The one name that always points at the current tree; it is replaced in place on every edit and never retired.
checkpoint
A name written automatically every time live moves, later thinned out by age; it is how "an earlier state of this file" exists at all after a plain edit.
history
A name written on purpose just before something destructive (a delete, a merge), with a reason attached, so the operation can be undone.
pin
A name that marks a point two files agreed on, kept until the operation that needs it is finished and then retired.
published copy
A second .burl file burl wrote from this one, stamped in both files with a shared copy id and a fork pin naming the root they parted at.
drain (import)
Merging a published copy's changes back into the notebook that published it, using the fork pin's tree as the common ancestor of a three-way merge.
base, mine, theirs
The three sides of that merge: the tree at the fork pin, this notebook's current tree, and the copy's current tree.
merge_conflicts
The queue a drain leaves behind: one row per block it could not merge, holding the three sides' object hashes, with mine left in the note.
write_conflicts
The other queue, for when two programs write the same open file at the same moment (a person typing and an assistant writing the same line), holding the losing text itself.

1. A task note becomes hashes

Start with a todo.txt note, five lines. burl splits the body on newlines, and each line is a block with its own stable id. The block's bytes are a fixed sequence of netstrings — <byte length>:<bytes>, — beginning with the tag; a field that may be absent is written as - when absent and + followed by a netstring when present. The block's hash is the SHA-256 of exactly those bytes. Note that the stable id is inside the hash: two blocks with the same text and different ids are different blocks, which is what lets a merge tell "one line retyped" from "one line moved".

Split and join: backend/src/burl/blocks.cr:12-22,131-140. Ids: blocks.cr:204-206 (UUIDv7 as 32 lowercase hex). Netstrings and the +/- marker: backend/src/burl/merkle.cr:340-369. Block bytes: merkle.cr:414-421. Digest: merkle.cr:461 (Digest::SHA256.hexdigest). ADR-0016 part 3 and its 2026-08-15 addendum.

The note object


A note's bytes are its scalar fields, then the count and hashes of its blocks in order, then the count and
hashes of its child notes. No row ids and no timestamps: a wall-clock value in the hash would make two devices
disagree about nothing. Editing one line therefore changes one block hash, which changes the note hash, which
changes every ancestor's hash, which changes the root.

2. How the history of root hashes is kept


Objects are never edited, only added, so every tree that ever existed is still in the store — until garbage
collection removes what nothing names. The names live in one table, merkle_roots(name, hash, kind),
and the rows differ only in lifecycle:


    
  
  • live the current tree. Exactly one row (a partial unique index says so); replaced in place on every write.
    • 
  
  • checkpoint written every time live moves, unless the newest checkpoint already has that hash; thinned into hourly/daily/weekly tiers by compact!.
    • 
  
  • history written by retain! before a destructive write, with a reason; pruned by count and age.
    • 
  
  • pin a fork point or an import's base/theirs tree; advanced or retired by the operation that consumes it. A pin with no live import is a checkable leak.
    • 



A drain is an event that both consumes named roots and produces one. It records itself in a second
table, imports, with four roots: fork_root (the base it merged against), theirs_root
(the copy's tree), pre_import_root (this file's tree just before, also retained as a history row),
and merged_root (the result). Afterwards the fork pin advances to theirs' root, not the merged root:
the merged root is not an ancestor of the copy, and diffing the next drain against it would read every home-side
change as a deletion on the copy's side.


Kinds and lifecycles: schema.sql:905-956, ADR-0026. live+checkpoint:
merkle.cr:1188-1233 (publish_root!, checkpoint!). pin!:
merkle.cr:1242; retain!: :1296; pruning: :1315,1358. The drain's
writes: backend/src/burl/import.cr:600-620 (history root, imports row, merged_root),
:634-635 (fork pin advance), :705-708 (base/theirs pins, only when something queued),
:711-716 (published_copies.consumed_root). Why theirs' root and not the merged one:
import.cr:156-165. What retires each pin: the table in backend/src/burl/conflicts.cr,
retire_pins_if_drained. The drain writes live through Merkle#rebuild!
(merkle.cr:1995), which does not name a checkpoint; the next ordinary save does.

    3. A sample task-note merge, block by block
    

    Home published a copy of the note; both then edited it; now home drains the copy back. The diff between two
trees descends only where hashes differ and matches notes by stable id, so a note nobody touched costs one string
comparison. For a note both sides touched, its scalar fields merge per field and its body merges per block, in
three tiers:
    

      
  
    1. One side changed it — take that side. Not a conflict.
      2. 
  
    2. Both changed it, in different places within the line — compose the two edits (Diff3). Not a conflict.
      3. 
  
    3. Both changed the same characters — keep mine in the note, queue theirs. A conflict, and it never stops the drain.
      4. 

    

    Two more rules apply in both directions: deletion loses to edit (a block one side deleted and the other edited
comes back with the edit), and a block only one side ever had is kept.

    What is conflict-free, and what is not
    

    Free of conflicts by construction: different notes; different fields of one note; different blocks of one note;
disjoint character spans of one block; identical edits made on both sides. Most of what a whole-note or whole-file sync
would have flagged is in this list. Not free, and queued: overlapping spans of one block; a scalar field
(title, parent, icon, format, extension, note-level formatting) changed differently on both sides — mine is kept and the
note itself is queued; a block with rich-text formatting on either side (no text merge can reposition the spans, so it
is not attempted). Not free, and not queued either: both sides reordering the same note's blocks differently —
mine's order stands and the drain reports the declined reorder rather than queueing it, because a conflict row's
three sides are objects that carry no ordering and would show a person two identical lines to choose between.
The rule throughout is that a conflict never blocks the drain: the queue is a to-do list, not a modal.
    

    Scalar collisions: import.cr:1979-2008. Rich spans: import.cr:2076-2083.
Reorders: import.cr:2128-2167 (the four answers; "why the last one is a rule and not a queued row").
Never blocks: import.cr:151-155, conflicts.cr:6-10. This page simulates the block tiers and the
re-mint edge; it does not simulate scalar fields, rich spans, or reorders.
    


    The fourth case: the re-mint edge
    

    The three tiers are defined over block identity. A whole-body write (set_body) gives a changed line a
fresh stable id, so if both files rewrite the same line that way, the drain never sees one block with two edits.
It sees the base block gone on both sides and one unknown block added on each — and an added block has no base to
compare with. Both survive as two lines, Diff3 never runs, and nothing is queued: the drain reports zero
conflicts and the note holds both versions. Press "Load the re-mint edge" above to watch it. The same two texts through
the editor path (identity kept) produce one block and one queued conflict.
    

    Evidence: backend/spec/import_remint_spec.cr — two examples, the second a control through
set_text, 0 failures. The branches that produce it: import.cr:2087 ("mine added it, theirs never
saw it") and :2096-2102 ("theirs added it"). Ordinal collision between the two survivors is re-keyed by
import.cr:2213 (rekey_collisions); their relative order there is decided by comparing device-suffixed
sort keys, which this page cannot know, so it shows mine first and says so.
    


    Resolving what was queued
    

    Every row in merge_conflicts names three objects by hash (base, mine, theirs), never text, and an
unresolved row is itself a garbage-collection root. What the resolver shows as mine is read live from the note,
because the block goes on being edited while the row waits. The person has three answers, and none of them is chosen for
them: Mine writes nothing at all (mine is already in the note); Theirs writes theirs' text over the block;
Edited writes text the person typed, seeded with the best composition the engine could make and the colliding span
highlighted. There is no "keep both": an engine has no basis to pick an ordering, so that was dropped once a person could
type instead. The assistant-facing MCP server can list both queues and resolve neither (ticket #149).
    

    Hashes, GC root: conflicts.cr:13-23, schema.sql:1023. Mine read live:
conflicts.cr:41-63 (#384). Resolution = Mine | Theirs | Edited: conflicts.cr:188-192;
resolve!: :365-412. The seed for Edited: diff3.cr:274-335
(compose_partial), ADR-0027. No keep-both: ADR-0016 amendment 2026-09-08. MCP read-only: ADR-0015, ADR-0027.
    

    



    Sidebar: the second queue, write_conflicts
    

    Everything above happens between two files. burl also lets two programs write one open file — the
person typing in burl and an assistant writing through the MCP server — and a collision there has none of a drain's
shape: no import to reference, no fork pin, and the losing text was never stored as an object, so there is no hash to
name. It gets its own table. The rules are the same three tiers, applied by Blocks#merge_buffer against the
block list the buffer was loaded from; what differs is what a collision does: the body keeps the version belonging to the
person at the screen (the caller says which side that is — there is no default), the incoming version is stored
as text in write_conflicts, the line carries a mark in the editor's gutter, and hovering the mark shows
both. A line can collect several incoming versions, so rows are numbered 1..N per line and answering one supersedes the
others. Before this table existed the collision wrote both versions into the body, one under the other, silently and
permanently — which is exactly the "keep both" the drain's resolver also refuses.
    

    The two queues are separate tables and separate counts: the drain's queue says nothing about the live one and
vice versa, which is how ticket #365 was found. Neither auto-resolves.

    Checking this page against a real .burl
    

    The hashes here are honest only if they are the same function of the same bytes as burl's. Two checks, both with stock
sqlite3:
    

    # 1. any object's hash is the SHA-256 of its body, byte for byte
sqlite3 -noheader notes.burl "SELECT hash, kind FROM objects LIMIT 3"
sqlite3 -noheader notes.burl "SELECT body FROM objects WHERE hash = '<one of them>'" | head -c -1 | sha256sum
#   (head -c -1 strips the newline sqlite3 appends; the body itself contains none)

# 2. the named roots, and that 'live' names a root object whose children are the top-level notes
sqlite3 -header notes.burl "SELECT name, kind, substr(hash,1,8) AS h, reason, created_at FROM merkle_roots ORDER BY created_at"
sqlite3 -noheader notes.burl "SELECT body FROM objects WHERE hash = (SELECT hash FROM merkle_roots WHERE kind = 'live')"
